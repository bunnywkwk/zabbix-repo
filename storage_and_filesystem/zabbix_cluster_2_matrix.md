# Implementation Matrix: Storage & Filesystem

This matrix evaluates every requirement under the `Storage & Filesystem` cluster from the RHEL Operational spreadsheet, pairing it with its explicit threshold from `Annex A` and justifying the technical approach in Zabbix.

### Engineering Philosophy for this Cluster
Our approach strictly utilizes Zabbix Agent 2's native **VFS (Virtual File System)** Go plugins. We intentionally avoid unsecure shell scripts running `df`, `findmnt`, or `awk`. We also utilize Zabbix's advanced Predictive trigger functions (`timeleft`) to satisfy trend-forecasting requirements without relying on external AI or scripts.

| ID | Title | Threshold (from Annex A) | Approach | Achievable? & Justification |
| :--- | :--- | :--- | :--- | :--- |
| **OBS-F-021** | Filesystem Capacity Trend | **Warn:** 80% OR 7 days to full<br>**Crit:** 90% OR 24 hrs to full | Filtered LLD (`vfs.fs.discovery`) + Predictive Triggers | **Yes.** Bypasses the need for external bash scripts. We use native Zabbix calculated triggers and the `timeleft()` predictive function. By deploying Filtered LLD, this rule automatically maps itself to every physical partition (`ext4`, `xfs`) while ignoring noisy virtual mounts (`tmpfs`). |
| **OBS-F-022** | Inode Utilisation | **Warn:** 80%<br>**Crit:** 90% | Filtered LLD (`vfs.fs.discovery`) | **Yes.** Fully achievable using 100% secure native keys, dynamically applied to all physical drives via LLD. |
| **OBS-F-023** | Filesystem Availability | Alert if missing, unresponsive, or mounted read-only (`ro`) | Native Global Check (`vfs.file.contents`) | **Yes.** Zabbix natively pulls mount options. We use a regex against `/proc/mounts` to instantly trigger a global alarm if the `ro` (read-only) flag is detected on any physical production volume. |
| **OBS-F-027** | Storage Performance (Latency) | **Warn:** > 20ms (5m)<br>**Crit:** > 100ms (5m) | Hypervisor Level (Hardware Dependent) | **Yes (Hardware Dependent).** The RHEL 9 kernel inside a Proxmox VM abstracts millisecond disk operations via VirtIO. Accurate storage latency metrics must be polled directly from the Hypervisor (Proxmox host) or the underlying SAN, rather than the Guest OS. |
| **OBS-F-025** | Storage Media Health (SMART) | Predictive failure / Reallocated sectors | Zabbix Agent 2 Built-in Plugin (`smart.disk.get`) | **Yes (Hardware Dependent).** Cannot be meaningfully tested on virtual disks (Proxmox VMs). On physical hosts, Zabbix Agent 2 natively queries SMART data without requiring root bash scripts. |
| **OBS-F-026** | Storage Redundancy | RAID degradation | Native Checks / IPMI | **Yes (Hardware Dependent).** Similar to SMART, software RAID can be tracked natively (`vfs.file.contents[/proc/mdstat]`), but enterprise hardware RAID requires controller-specific IPMI/SNMP templates. |
| **OBS-F-028** | Logical Volume Monitoring | Pool capacity < 10% / Thin-pool metadata | `UserParameter` (LVM) | **Partial (Requires UserParameter).** Zabbix does not currently possess a native Go plugin for querying LVM thin-pool metadata. A secure `UserParameter` explicitly invoking `vgs` or `lvs` with restricted sudo permissions is the standard architectural workaround. |
| **OBS-F-029** | Backup Outcome Monitoring | Alert for failed/overdue jobs | Zabbix Trapper / API | **Yes (Architectural Integration).** An OS agent cannot natively know if an enterprise backup appliance (e.g., Veeam) successfully backed it up. This is resolved by having the Backup Server send a push notification to a Zabbix Trapper item. |
| **OBS-F-030** | Backup Storage Capacity | **Warn:** 75%<br>**Crit:** 90% | Native Check (`vfs.fs.size`) | **Yes.** If the destination is mounted to the Linux OS, standard native checks apply. If it is an external appliance, API templates are used. |
| **OBS-F-031** | Restore Verification | Alert on verification failure | Zabbix Trapper | **Yes (Process Dependent).** Similar to OBS-F-029, a Zabbix Trapper item waits to receive a payload from the team's automated CI/CD restore-testing pipeline. |
